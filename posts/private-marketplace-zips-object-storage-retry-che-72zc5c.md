# Private Marketplace ZIPs: Object Storage Retry Checks for Multipart Uploads

Treat a private marketplace export as unpublished until its multipart upload is complete, its final object has been checked, and a database pointer names that verified object. Short answer: when a ZIP download is incomplete or corrupted, stop retrying the browser request and inspect the upload state, missing parts, completion result, object size, and cache headers in that order.

That ordering protects the large-file throughput SLO. A generator can finish producing bytes while the object-storage control plane still has an unfinished upload, and a download link issued in that interval turns a recoverable worker failure into a customer-visible archive failure. The worker needs a state machine, not a hopeful URL.

## Why do multipart export uploads produce incomplete ZIP downloads?

ZIP is a useful boundary because its central directory is written near the end of the archive. A missing tail can leave a downloader with a file that looks substantial but cannot be opened; a missing middle range can damage a member even when the final byte count happens to look plausible. The browser is reporting the symptom. It is rarely the right place to start the investigation.

For a marketplace export, reserve an attempt-specific key such as `exports/{tenant}/{job}/attempt-{n}/catalog.zip`. Record the expected byte count from the exporter before uploading, the upload identifier returned by storage, the planned part numbers, and the checksum or digest used by the application. Persist the identifier before sending part 1. Otherwise a worker restart can leave the team knowing that something exists but not which multipart state belongs to the job.

The failure modes are more mundane than the ZIP error suggests:

- The producer stopped after writing only some parts.
- A part retry used the wrong part number or replaced a part with a different byte range.
- The final complete operation was skipped after a timeout, or its response was never recorded.
- A second attempt wrote beside the first while the published key still referred to an unverified object.
- A proxy or browser cache served an older response after a corrected export was published.

Don't infer completeness from the number of successful upload requests. A successful part request proves only that one numbered part was accepted; it does not prove that the assembled object is complete or that its ZIP directory is readable.

## What should an object storage runbook check before retrying a ZIP export?

Start with the job database, then storage metadata, then the delivery path. That sequence keeps an operator from repairing the wrong attempt.

First, compare the job's generated byte count and planned part count with the durable part ledger. The ledger should contain one record per part number, the byte length sent, the digest calculated before transmission, the response status, and the attempt identifier. A retry may replace a part, but it must not silently create a new attempt or change the expected total without a new job revision.

Second, inspect the result of the completion operation. A worker should store whether completion was acknowledged and the object key it returned or finalized. If the completion call timed out, treat the state as unknown until a metadata read resolves it; do not immediately start another writer against the same key. A `429` is a retryable control-plane signal only when the service's policy says so, and a backoff should preserve the distinction between a rate limit and a malformed request.

Third, issue a metadata request against the finished object and compare its size with the exporter count. The check is a publication gate, not a diagnostic flourish. If the size differs, hold the link. If the object is expected to be a ZIP, a separate archive check should read the central directory in a worker sandbox before the pointer changes. The metadata check catches truncation; the archive check catches some forms of internal corruption.

The evidence should be boring and queryable. A useful incident record has the job ID, attempt ID, object key, upload ID, expected bytes, observed bytes, completed-at timestamp, validation result, and publication timestamp. Keep response bodies for rejected control-plane calls, with secrets removed. Logs that say only `upload failed` are not an operational interface.

One short rule:

Never publish from a part-upload callback.

This Go example shows the narrow validation gate. It deliberately accepts metadata rather than making a provider-specific request, so the same test can sit behind different object-storage adapters.

```go
package main

import (
	"errors"
	"fmt"
)

type ObjectMetadata struct {
	Size       int64
	ContentType string
	ETag       string
}

func validateArchive(meta ObjectMetadata, expectedSize int64) error {
	if meta.Size != expectedSize {
		return fmt.Errorf("archive size %d does not match expected %d", meta.Size, expectedSize)
	}
	if meta.ContentType == "" {
		return errors.New("archive metadata has no content type")
	}
	if meta.ETag == "" {
		return errors.New("archive metadata has no validator")
	}
	return nil
}
```

The validator is intentionally not a ZIP parser and not a substitute for a digest check. It is the cheap gate before publication; a full archive read belongs in the export worker's verification step, where the team can enforce its own maximum scan time and memory budget.

## How should a marketplace worker complete, retry, or abort multipart uploads?

Model the workflow as durable transitions: `created`, `uploading`, `complete_pending`, `completed`, `verified`, `published`, and `aborted`. Only `verified` may move the user-facing pointer. Each transition needs an attempt ID and an update that is safe to replay after a process crash.

The happy path is simple: create the multipart session, save its identifier, stream numbered parts, record each accepted part, complete the session with the recorded parts, read final metadata, validate the archive, and atomically update the database pointer. The download service reads that pointer and generates an expiring link from the pointed-to key. It never guesses the newest object by listing a prefix.

Retries need two different policies. A failed part can be retried with the same part number after a bounded backoff, provided the bytes and attempt ID are still the same. A timed-out completion needs reconciliation before another completion or another upload is started. Use an idempotency key for application-level job transitions, because a storage operation's network timeout does not tell the worker whether the server applied the write.

Abort is part of the normal lifecycle. If generation fails, a required part cannot be reconstructed, validation rejects the finished object, or the job is cancelled, mark the attempt as aborting, invoke the storage adapter's abort operation, and record the outcome. If abort itself is temporarily unavailable, keep the attempt visible to cleanup rather than marking it clean. Capacity planning must include this queue of abandoned multipart state: a large export fleet can exhaust storage through forgotten fragments long before the successful archive volume becomes alarming.

For throughput, choose part size from measured worker memory, network bandwidth, and the recovery cost of replaying a part. Larger parts reduce request overhead but make a retry more expensive; smaller parts improve retry granularity but increase control-plane traffic and ledger entries. The right value is workload-specific. I'm not sure a single size remains correct as marketplace exports grow, so the part-size choice should be a configuration with a throughput test and an explicit upper bound, not a constant hidden in a helper.

## What are the buy-versus-build trade-offs for private export delivery?

The real choice is who owns the state machine, durability controls, and on-call evidence. A managed object store usually supplies the multipart primitives and lifecycle controls; a self-hosted system may offer deployment control but transfers disk failure, upgrades, replication, and recovery testing to the platform team. A storage abstraction can reduce application coupling, but it cannot erase differences in retention, conditional writes, eventing, or public-delivery behavior.

| Approach | Good fit | Operational trade-off | Check before committing |
| --- | --- | --- | --- |
| Managed object storage | Teams that want provider-operated durability and lifecycle primitives | IAM, quotas, egress policy, and service-specific semantics remain part of the design | Confirm multipart completion, abort, metadata, and retention behavior |
| Self-hosted object storage | Isolated environments with staff and hardware ownership | The team owns disks, replication, upgrades, restore drills, and paging | Prove recovery time and capacity headroom under failed uploads |
| Application-managed archive store | Small files or a tightly controlled persistence layer | Large-file retries and download delivery become application concerns | Measure memory, throughput, range handling, and failure recovery |

The catch is that a solution optimized for large-file throughput may be unsuitable when the business requires immutable retention, cross-region recovery, or a public download surface with policy controls that the chosen storage layer does not provide. In that case, choose the option whose documented retention and delivery primitives satisfy the requirement, even if its API is less convenient. Stick with the simpler application path for small exports; multipart coordination is a liability when the object is small enough to write and validate in one bounded operation.

Price should be a secondary input. The expensive failure is an export that must be regenerated, investigated, and explained to a customer, so the capacity model should include request overhead, retained incomplete parts, validation reads, egress, and on-call time rather than comparing a single storage line item.

## How do verification, cache control, and rollback close the incident?

Publication should be an atomic pointer change from the last verified key to the new verified key. The download endpoint creates an expiring link only after reading that pointer. This gives a failed retry somewhere to land without overwriting the archive that customers can already retrieve, and it makes rollback a database operation instead of a race between a worker and an active downloader.

The delivery check has its own branch. RFC 3986 defines percent-encoding for URI components; object keys containing reserved characters must be encoded according to the link builder's component rules, or a valid object can be addressed as a different path. Cache-Control then determines how intermediaries may reuse a response. Review the response policy for expiry, private data, and re-download behavior; a stale cached error can survive after the storage object has been fixed, while an overly long public cache lifetime can outlive the authorization decision.

Verification is complete only when the part ledger is complete, the completion result is durable, final metadata matches the generated bytes, the archive check passes, the link points at the verified attempt, and the response policy is appropriate for private data. If any check fails, leave the old pointer unchanged, abort or queue cleanup for the failed attempt, and retry under the export SLO.

That's the rollback.

The durable lesson is narrower than “use multipart uploads.” For private marketplace downloads, the important boundary is the moment an independently verifiable object becomes the published object. Keep that boundary explicit, observable, and reversible, and an incomplete archive stays an internal job failure instead of becoming a customer download.
